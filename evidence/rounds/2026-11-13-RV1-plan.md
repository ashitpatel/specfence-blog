## PB1: decisions come from the base

**The hole, read from the code (2026-11-13).** `review_diff`, `review_commits`, `lazy_check` and the
post-commit guard read person-decided state from the tree under review:

| state | where it is read | what a change could do by editing it |
|---|---|---|
| sharing and typed answers (`answers.yaml`, `answers.json`) | `review/diff.py` proposes on the head tree; `touched_proposals(head_root, …)` | **corrected at build:** a `scope: unused` answer hid the touched proposal (shown); a sharing answer did not reach the touched flags (`touched_proposals` proposes without answers), so that example was wrong |
| screen status (`slices/choices.jsonl`) | `review/touched.py` `_statuses(head_root)` | mark a touched proposal "screened: falsified", so the flag reads as already examined |
| deployment answers and confirmation (`deployment/*.json`) | **corrected at build:** `propose(head_root, service)` infers from the tree's deployment files, which are configuration under review (already reported as `deployment_files`), and reads no stored answer | nothing through the review today; still covered by the redirect, since other readers reach the stored models |
| scan policy (`policy.yaml`) | head tree | shrink the screen |
| golden store (the `--store` file, e.g. `.specverify/golden.json`) | `guard/hook.py` reads it as committed (`store_path`) | drop or edit a property in the same commit that breaks it: the guard judges against the weakened store. BT1 listed "a property removed by hand is not detected" as an open limit; PB1 closes it for the guard |

`review_commits` exports both refs with `git archive`, so any of these files tracked in the repository arrive in
the head export exactly as the change wrote them.

**The rule.** For a review of base → head:
- **The verdict side reads person-decided state from the base:** answers, choices, deployment, policy and the
  golden store. The code, the specs and the facts still come from the head. That is what is being reviewed.
- **Every difference between the base's and the head's person-decided state is reported** in a new section,
  `decision_changes`. Each entry gives the file, the subject (an answer, a proposal id, a dimension, a property)
  and the before and after values, with the note "applies once a person accepts it; this review used the base's".
- **A golden property removed or edited in the commit under guard is reported at BLOCKING level**, even when every
  remaining property holds. The person can still drop a property; it now takes its own commit, and it shows.
- **Unchanged when there is no base.** A first look and a single-tree `first_look_report` read their own tree, as
  today.

**Steps:**
1. `review/decisions.py`: `DECISION_STATE` lists the person-decided files (one home). `read_decisions(root)`
   loads them, and `decision_changes(base, head)` diffs them per subject.
2. `review/diff.py` and `review/touched.py` take a `decisions_root` (the base) for every person-decided read:
   - `_statuses` and the sharing answers used by `touched_proposals`;
   - `propose(…)` for deployment.

   They keep `head_root` for code and specs. The output gains `decision_changes`.
3. `guard/hook.py` and `guard/jit.run`: load the store from the parent commit (`git show <parent>:<store>`), not
   the working copy. A diff against the commit's copy goes into the report as `golden store changed in this
   commit`. A removed or weakened property is BLOCKING.
4. `lazy_check(base_root, head_root, …)` uses the same split.
5. Skill text in `review-diff.md`: read `decision_changes` to the person first; never treat a head-side answer as
   given.
6. Tests (`tests/test_review_decisions.py`), one per row of the table:
   - a head-only "not shared" answer does not close a touched proposal, and shows in `decision_changes`;
   - a head-only falsified screen leaves the proposal "unscreened";
   - a head-only deployment change re-checks under the base's model;
   - a head-only policy change keeps the base's screen;
   - a commit that removes a golden property is BLOCKING.

   Each new filter gets a mutant (memory: calibrate and mutate).
7. Bars (tuning §3): `tools/dev/shadow/run.py` on the label sets plus klipper-20 must show no loss. A first look
   is unaffected by construction, which the byte-identity bar on `generate_skeleton` confirms. The replay is N/A:
   no recorded call is a review of two trees whose decision files differ. That is to be checked and recorded,
   not assumed.

**Risk: a change that legitimately carries new answers.** A PR in which the person answers a new question
(after a requirements change, say) would be judged under the old answers until merged. That is the intended
cost: the review says so in `decision_changes`, and the person re-runs it after accepting them. The owner decides
whether this is acceptable (decision 1).

## IP1: introduced, pre-existing, touched

**Today.** `review_diff` already computes, per re-checked spec:
- `restores`: violated at base, holds at head;
- `breaks`: holds at base, violated at head.

It also flags touched proposals (`how`: writes its state, in its functions, new with this change). A violation
present on **both** sides is reported as a violation, without saying it predates the change. Touched proposals
say how the change reaches them, not whether the risk is the change's own.

**The rule.** Every finding-like entry gains `origin`:

| origin | meaning | from |
|---|---|---|
| `introduced` | the change creates it | `breaks`; a touched proposal `new with this change` (N1) |
| `pre-existing` | it was there before; the change does not create it | a violation at base and head alike; a touched proposal that exists on the base with the same code hash (RM1's `code_hash`, so the hash does the comparing) |
| `touched` | it existed before, but the change edits its code | a touched proposal on the base whose code hash changed |
| `resolved` | the change removes it | `restores` |

**Steps:**
1. `review/diff.py`: label `restores`, `breaks` and both-sides violations. `review/touched.py`: compare the base
   and head `code_hash` per proposal id (RM1 put the hash on every proposal).
2. The summary line counts by origin: "1 introduced, 2 touched, 4 pre-existing".
3. Skill text: lead with introduced, then touched. Pre-existing go last and are never called the change's bugs.
4. Tests: one per origin on the `slices/single` fixture, editing a function between base and head, plus a mutant
   per rule.
5. Bars: as PB1. IP1 adds fields only, so verdicts cannot move, but the replay compares whole outputs, so the new
   keys must be ignored or recorded.

## NF1: when a check may fail

The rule, recorded in plan §12.2 (gates) for any future hosted check or CI integration of the guard:
- the check concludes failure only on a BLOCKING item: a curated golden property that held and fails now, or (PB1)
  a property weakened in the same commit;
- everything else (WARN, FYI, touched flags, pre-existing violations, `decision_changes`) is neutral;
- the check never approves.

No code. The guard's ranks (`guard/rank.py`) already make the distinction.

## Out of scope here: the race-claim bridge

The comparison's most promising idea is not borrowing: specfence as the verifier for race claims that
CodeRabbit or Claude Code Review write in prose. It needs its own plan, starting with how a prose comment maps to
a proposal. It is listed here only so it is not lost.
