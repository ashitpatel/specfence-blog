**EH-M passes.** All four pre-registered mutants are detected, and the control (no change) passes clean. So the

## Deviations

- **D1, a harness defect, fixed.** The first mutant run reported 0 of 4 detected, because the tests had imported
  the checkout and not the mutated copy. The repository's `pyproject.toml` sets pytest's `pythonpath = ["src"]`,
  and that setting beats `PYTHONPATH`.
  - The runner now copies the test file and `conftest.py` beside the mutated `src`, under its own `pytest.ini`.
  - It also runs a control first. The control passes, and the four mutants are then detected.
  - Every run checks that it imported the copy.
- **D2, one more category: "forgeable".** Some routes clear a reason only by writing into the engine's own state
  logs (`questions.jsonl`, `scenarios.jsonl`) by hand. No tool does that, so such a route is forgery, not a hatch.
  These routes are recorded apart. Pinned driver mode (BT1) is their guard: an envelope must back every record.
  The pre-registration's limits section anticipated this ("hatches that need no lying"). The category was set
  before the tests were written.

## Decisions for the owner

Each hatch can be closed by adding a step for the person, at the cost of one more question, or kept and marked
**no check** in the skill. The false-positive ruling (2026-10-29) leans toward asking. Each decision is the owner's.

1. **The answers file, for scenarios and NFR dimensions.** The file is documented as the person's, but the skill
   tells the agent to transcribe approvals into it.
   - **Option:** read it only when the client cannot elicit, and only when it was present before the run started,
     recorded by hash at `begin_run`.
   - **Or:** require pinned mode for headless runs.
2. **Fresh readings.** No mechanism can prove a context was fresh: EG1 already says "**No check**".
   - **Option:** mark the gate advisory in `forge_done`'s output ("readings recorded, not proven fresh").
   - **Or:** accept readings only from a subagent the engine starts itself, which it cannot do today.
3. **Untagging to clear `unstated-guard`.**
   - **Option:** check guards on every action that changes state a tagged property reads, not only on tagged actions.
   - **Or:** report a `@req` tag removed since the last run.
4. **The requirements document.** This one has the widest reach.
   - **Option:** record a hash of each requirement's text when the person accepts the scenarios or answers a
     question about it. `done_check` then lists any requirement deleted or changed since, as a question to the
     person.
5. **A person confirming a wrong claim.** That is what FC1 agent3 found. It is not a hatch, so no code audit can
   close it.
   - The confirmation question could show the requirement that most suggests an outside input, "R7 says paid",
     beside the claim. That is a wording change, and it is untested.

## Limits

- **The audit is not blind.** Its author also wrote EG1's fresh readers, which are now a confirmed hatch.
- **One reason per route.** The requirement-deletion route is shown for `uncovered` alone. The other reasons that
  name a requirement share the route, but are not tested one by one.
- **The C rule is narrow.** A spec edit the checker judges counts as closed, even when the edit itself asks
  nobody, for example adding a stuttering step to clear `can-get-stuck`. Those edits are where the skill's "ask the
  person" instructions matter, and SL1 and RH1 showed those instructions cannot be checked from the text.
