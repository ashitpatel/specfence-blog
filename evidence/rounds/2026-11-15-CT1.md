# CT1: a control marker explains a failure only beside a real check

- **The hatch:** CM1 row D2 (`2026-11-15-CM1-results.md`). One `\* @control <reason>` line on a spec's only cfg moved
  its violation out of section 2 and into `depth.controls`.
- **The owner's decision:** "Lone control stays a finding (Recommended)" (`decisions/2026-11-15-owner-decisions-ct1.md`).

## What changed

**Where a control's failure goes** (`survey/report.first_look`):

| the cfg | where its violation or deadlock goes |
|---|---|
| marked `@control`, with a real check beside it | explained as an expected failure, as before |
| marked `@control`, with no real check beside it | **section 2**, labelled "marked as a control (<reason>), but no real check sits beside it…" |

A real check is a cfg that is not a control (`real_check_beside`), either:
- on the same spec;
- on the spec it is the control of (`<Spec>.tla` beside `<Spec>Control.tla`).

**Both entries show it:**
- the `depth.controls` entry gains `lone_control: true`;
- so does the check's own entry.

**What did not change:**
- A control spec's unmarked cfg already stayed a finding.
- Controls beside a real check are unchanged.

**The skill.** model-slice's control paragraph states the rule, marked **checked**: CT1. It also says never to mark
the check that found a violation as a control.

## Limits

- **An agent can add a trivial non-control cfg beside the marked one,** for example one that checks only `TypeOK`.
  The violation is then explained again. The trivial cfg's check shows "NOT shown able to fail" for a vacuous
  property, but one that checks a real, unrelated property passes as a real check.
- **Whether a control is a fair control is still not judged.**
- **No agent trial was run.**
