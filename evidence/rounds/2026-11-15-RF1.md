# RF1: the answers file as it stood when the run began

- **The owner's decision:** `docs/project/decisions/2026-11-15-owner-decisions-rf1.md` ("Freeze NFR, audit
  scenarios").
- **The hatch:** EH1's answers-file hatch, for scenarios and NFR (`2026-11-15-EH1-results.md`).

## What was built

- **`forge/frozen.py`**
  - `begin_run` calls `freeze`, which records the answers file's sha256 (or `null`, when there is no file) in
    `.specfence/answers-frozen.json`, once.
  - A later `begin_run`, `fresh` included, keeps the first record, so the agent cannot re-freeze a file it wrote.
- **Answers-file provenance** (`deploy/answers.py`) now carries the file's `sha256`, so every record made from the
  file says which bytes it came from.
- **NFR is frozen** (`forge/nfr.py` `done_reasons`).
  - The file's answers fill the greenfield model only when the file is byte for byte the one the run began with.
  - An answer the store recorded from any other bytes is owed again, with "answered from an answers file the run
    did not begin with".
  - With no run start recorded, the file answers nothing.
- **Scenarios are audited** (`forge_done`). A new field, `accepted_via_answers_file`, lists each scenario accepted
  through the file, with its client, its file, and `after_run_began` (true, false, or null when no run start was
  recorded). Acceptance through the file itself is unchanged.
- **The skill** (`refine-requirements.md`):
  - step 1b: a file answer counts only from the file the run began with (**checked**);
  - step 8: show the `accepted_via_answers_file` list to the person in the final report (**no check**).

## Evidence

- **`tests/test_forge_frozen.py`: 12 tests.**
  - The freeze records once; a missing file is recorded as `null`.
  - NFR counts the original file, but not a file written later, a file changed later, or a file with no run start.
  - A stored answer from a later file is owed again; an elicited answer is untouched.
  - Provenance carries the hash, and `late`'s three values are tested.
  - Through the tools: a client with no elicitation runs `begin_run`, the approvals are transcribed into the file,
    `accept_scenarios` still accepts them, and `forge_done` lists them as after the run began.
  - A signed driver envelope still answers NFR when there is no run start (the freeze covers the file only).
- **EH1's tests, updated:**
  - the NFR row is now **closed** (no run start, or a file written after it);
  - the scenario row stays a hatch, now audited;
  - the completeness count for `nfr.done_reasons` goes up to its two producers.
- **`tests/test_forge_nfr.py`:** the headless-file test now freezes first, as `begin_run` would.
- **`tests/test_bt1d_profile.py`:** its answers-file helper now freezes, as `begin_run` would.
- **Mutation: 9 of 9 detected,** with a clean control (`tools/dev/rf1/mutants.py`, over `test_forge_frozen.py` and
  `test_bt1d_profile.py`).
  1. a later freeze replaces the record;
  2. the file always counts;
  3. NFR reads the file without the freeze;
  4. stored file answers are trusted;
  5. `begin_run` does not freeze;
  6. `forge_done` lists nothing;
  7. provenance has no hash;
  8. `late` never flags;
  9. the envelope is dropped along with the file, which was the first build's bug.

## Deviation: the first build dropped the driver envelope

- **The bug.** The first build skipped `apply_answers_file` whenever the file did not count, and that also dropped
  the signed envelope's answers.
- **How it was found.** The full suite caught it: 3 failures in `test_bt1d_profile.py`.
  - The pinned-envelope test was a real regression.
  - The other two wrote an answers file with no run start, which is the intended new behaviour, so their helper
    now freezes.
- **The fix.** `apply_answers_file` and `file_profile` take `with_file`, so the envelope is applied either way.
- **The guard.** A same-profile envelope test and mutant 9 now pin it. The BT1d test alone did not catch mutant 9,
  because it reaches the envelope through the profile-correction path.

## Limits

- **A file the agent writes before `begin_run` is frozen as the person's.** The skill calls `begin_run` first.
  Without elicitation, no channel can tell who wrote a file that already exists.
- **A person who edits their file during the run loses its NFR answers.** They are owed again, and have to be
  given by elicitation or by the envelope. That is the cost of the freeze.
- **The freeze record is a state file.** Deleting it by hand is forgery, as with the other state logs.
- **The scenario audit does not block anything.** Showing the list to the person is **no check**. A person
  reading the final report can see that the file changed after the run began, and nothing more.
- **Code mode is unchanged.** Deployment answers, evidence policy, sharing and the rest still read the file
  directly, as persona and clean-room runs write it before the run. Only the greenfield NFR gate is frozen.
- **Pinned mode** never reads the file, so it is unaffected.
