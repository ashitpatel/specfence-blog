# FR3: fresh readers the engine runs itself, and a label for those it did not run

- **The owner's decision:** `docs/project/decisions/2026-11-15-owner-decisions-fr3.md` ("Engine-run when set, else
  advisory").
- **The hatch:** EH1's fresh-readings hatch (`2026-11-15-EH1-results.md`). The canary caught a reader that copied
  the drafting conversation, but not a drafting agent that wrote "a reading" itself.

## What was built

- **`forge/readings.py`**
  - **`reader_command`** reads `SPECFENCE_READER_COMMAND` from the server's environment, for example `claude -p`,
    `codex exec` or `gemini -p`.
  - **`run_reader`** runs that command with the brief as its last argument, in a new empty temporary folder, with
    stdin closed, and captures what it prints. It is refused when the command is missing, fails, or runs past its
    time limit.
  - **`run_fresh_readers`** issues two formalize briefs and one restate brief and runs a reader for each. It finds
    the reading in each output: the fenced block with the `@reading` line, or the first JSON object with `items`.
    It then compares the readings and records them with `engine_run: true`.
  - **`compare_readings` and `record_reading`** take `engine` (default false). The MCP tools never pass it, so an
    agent-supplied reading is always recorded as not engine-run, with `proven_fresh: false` and an origin ending
    "recorded, not proven fresh".
  - **`done_reasons`:** when a reader command is set, only engine-run results count, and the reasons say to call
    `run_fresh_readers`. With none set, the gate is unchanged.
  - **`proof`** gives the gates their `fresh_readings` field: "proven fresh: run by the engine", or "recorded, not
    proven fresh".
- **The MCP server:** a new tool, `run_fresh_readers` (79 tools). `done_check` and `forge_done` now report
  `fresh_readings`.
- **The skill** (step 6b): call `run_fresh_readers` when the person set a command (**checked**). Otherwise say in the
  final report that the readings are not proven fresh (**no check**).
- **The guide** (`egm-and-fresh-readers.md`): how to set the command, and what it costs, which is three CLI runs
  per round, billed to the person.
- **The counts:** README and getting-started now say 79 tools.

## Evidence

- **`tests/test_readings_engine.py`: 7 tests.** They use a fake reader command, a Python script that answers each
  brief and logs what its folder held.
  - Engine-run readings clear the gate and are labelled proven.
  - Each reader runs in an empty folder and never sees a canary.
  - With a command set, agent readings do not count. This is the EH1 hatch, closed.
  - With none set, agent readings count but are labelled.
  - Refusals: no command, a missing binary, a non-zero exit, zero readers.
  - The extraction from a chatty answer.
  - `done_check` reports the label.
- **EH1's tests:**
  - the readings row asserts the label in the advisory case;
  - the completeness count for `readings.done_reasons` goes up to its six producers;
  - the test pins the case with no command set, so a runner environment that sets one cannot flip it.
- **Mutation: 7 of 7 detected,** with a clean control (`tools/dev/fr3/mutants.py`).
  1. the gate counts agent readings with a command set;
  2. agent readings are recorded as engine-run;
  3. engine readings are not marked;
  4. the reader runs in the project folder;
  5. the label says proven for agent readings;
  6. a failing reader is accepted;
  7. the gates drop the label.

## Limits

- **No real CLI was run.** The tests use a fake reader. Whether `claude -p`, `codex exec` or `gemini -p` give
  readings in the expected shape, and how long they take, is not measured. Their output formats may need more
  extraction rules.
- **An empty folder is not a blank mind.** A fresh CLI session still loads the user-level instruction files (EGM's
  own documentation warns of this, `docs/harnesses.md`). The engine controls the folder and the prompt, not the
  user's global configuration.
- **A command that ignores its input still passes.** A person could set a command that is not an agent, or one that
  prints a fixed reading. The command is the person's choice, and the engine trusts it, as pinned mode trusts the
  public key.
- **Cost:** three CLI runs per round, billed to the person's account. Nothing runs unless the person sets the
  command.
- **Without a command, the hatch is still open,** but labelled. That was the owner's choice for setups without a
  reader CLI.

## A real reader run, 2026-11-15

The owner asked for it ("Try claude -p"). One run of `run_fresh_readers`, with this command:

```
claude -p --model claude-sonnet-5-5 --strict-mcp-config --mcp-config <empty> --permission-mode dontAsk --allowedTools '' --no-session-persistence
```

The command mirrors the FC1 driver's: no MCP servers and no tools, so a reader can only read its prompt and answer.

**The example.** Two requirements:
- R1: "Every expense has one owner".
- R2: "The approver of an expense is not its owner".

The drafted model carried a defect, `fact NoSelf { all e: Expense | e.approver != e.owner }`. That compares the whole
set of approvers with the owner, so an expense its owner approves, alongside someone else, is allowed. The files
are in `~/projects/benchmarks/fr3-real/`.

**The result.**
- **Timing:** about 7 seconds per reader, and 22 seconds for all three, comparison and restatement included.
- **Extraction worked** on the CLI's real output. Both formalize readings parsed and type-checked, and so did the
  restate JSON.
- **The seeded defect was found by both readers.** Each wrote `no (e.approver & e.owner)` on its own, with an
  `-- unclear R2` note that the text gives no multiplicity for the approver. Alloy reported one `reading-differs`
  finding on R2 for each reader: "your model allows this situation under R2 and reader 1 forbids it".
- **The restatement marked both R1 and R2 unclear.** For R2 the reason is real: one approver or several. For R1 the
  reason is weak: "owner" is not defined, and "one" could mean at most one. That is the advisory reader's noise. It
  costs the person one question each.
- **The gate** then listed 4 owed questions (2 reading-differs, 2 unclear), and `proof` said "proven fresh: run by
  the engine".

**What this does and does not show.**
- It shows that the engine-run path works with a real CLI, and that on a seeded drafting error the independent
  readers catch it.
- It is one example with one model, and the defect was seeded. It is not the seeded-defect measurement plan 5.3/5.4
  owes, which still needs a pre-registration.
- The readers also loaded the user-level `~/.claude/CLAUDE.md`, as any `claude -p` does. Their empty folder had
  nothing else.
